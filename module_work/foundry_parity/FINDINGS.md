# Funhouse wiring on Foundry: what still holds (audit, 2026-11-03)

The owner's question: "Storage is key to a functioning app. Anything else that might break the kind of wiring we had in Funhouse?"

**How this was done.** Read only. I read the code paths a session takes when `GEOTECH_DEPLOYMENT=foundry` is set (`webapp/foundry_entry.py` sets it), on master as of 2026-11-03. Alongside: `docs/FOUNDRY.md`, the BACKLOG items named below, and the AI FDE's private setup notes and build notes (read, not quoted). Nothing was run on Foundry.

**Two facts frame every row.**
- The last record has the published app still on the first test wheel of 2026-10-20, with the AI FDE's two workspace shims (BACKLOG INF-40, entry of 2026-10-27). Everything below marked "in master" has not been seen in a published app yet.
- Conversations, uploads and deliverables live inside the published container and are lost on a rebuild or a republish. That is BACKLOG INF-38, already being handled, so it is not a row here.

## Checks only Foundry can settle (one line each, for the FDE brief)

- **U1.** When the shared pool is exhausted, what status and error name does the Anthropic proxy route return? Capture one, during an ingest batch or with a burst of small requests on the Sonnet RID; send the status and `errorName`, never the token.
- **U2.** In the published app, run Connection diagnostics and send back the "reference PDFs" line. Also say whether the workspace repo took the PDFs in `references/`.
- **U3.** On the new wheel, in the published app: save a file, preview a PDF's pages, then "Prepare download" a conversation, restore that zip in a fresh browser session and confirm it opens with its cards. Time one click on a conversation with about 20 files.
- **U4.** Opened by two different people, which request header names (names only, never values) does `st.context.headers` show in the published app? Is `FOUNDRY_TOKEN` the publisher's, the app's or the viewer's?
- **U5.** Does the published container stop, sleep or restart when idle, overnight, or on republish? Leave a conversation overnight and check the list in the morning. What are the container's memory and CPU limits?
- **U6.** Does `FOUNDRY_TOKEN` expire while the published container runs? Read its expiry in the terminal without printing it, or run a turn in a tab left open for 12 hours or more.
- **U7.** Send back the "versions" and "optional packages" lines of Connection diagnostics from the published app: numpy, scipy, and whether `pynite` is listed.
- **U8.** Ask for a figure that needs plotting code (for example, a Mohr circle with custom labels). `activity.jsonl` should show `plot_code` finishing, not "the box could not start".
- **U9.** What is the largest PDF the published app's uploader accepts? Try about 50 MB and about 150 MB.
- **U10.** Can the publisher read the published app's server log (stdout and stderr) anywhere in Foundry?

## Noted (small, one line each)

- `webapp/app.py:537`: the conversation filter's "try Permanent storage below" points at a block Foundry does not draw.
- `webapp/diagnostics.py:433-441`: the missing-PDF advice names SharePoint, `stage_sharepoint` and `run_on_databricks`; on Foundry it should name the `references/` folder.
- `docs/FOUNDRY.md` §3 table: the `GEOTECH_WEBAPP_DATA` row says saved conversations survive restarts, which its own Notes section (INF-38) contradicts for a published app.
- Streamlit's usage statistics are on under Foundry's own start-up (the Databricks launcher turned them off); the result is only blocked outbound calls.
- OpenCV on a FIPS host hides `find_like` by itself (planlens test-loads it in a child process); nothing to do unless Foundry turns out to be FIPS.
- Sonnet's prompt cache did not always hit through the proxy (2026-10-20); this costs tokens, not answers.
- A screenshot pasted or a file dropped into the chat box uses the native uploader (Foundry's mode). It is untested in the published app.
